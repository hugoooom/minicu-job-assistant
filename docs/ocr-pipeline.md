# 单账号 JD OCR 流水线

采集仍使用一个已登录的 Edge 配置、一个任务标签页和一条页面 CDP 连接。
导航、登录检查、滚动、测量和截图全部由主线程串行执行。没有增加账号、无登录访问或并发页面。

对于需要 OCR 的正文，先保存该岗位全部分段截图，再写入 `岗位ID-description-captures.json`。
清单保存岗位 ID、分段顺序、截图比例、正文相对坐标和完整标记。
只有清单完整时才提交本地 OCR；截图中途登录失效、岗位切换或布局变化时不提交。

一个后台工作器独占并复用 JD OCR 模型，只读取本地图片及清单，不访问浏览器。
主线程可以处理下一岗位；包括运行中的任务在内，最多保留两份待识别 JD。
薪资采集本轮仍沿用原有同步方式。

结果按原岗位对象回收，由主线程统一更新 `jobs.json`。`ocr_pending` 不计入成功。
单个 OCR 失败记录为该岗位错误；访问受阻或第一次 Ctrl+C 时，回收已经提交的本地任务后保存退出。
OCR 运行中的原生计算不能立即强制取消，因此退出可能需要等待当前识别完成。
强制结束进程后可用已保存的完整清单重试；旧版没有完整清单的截图不支持直接重试。

## 使用

原采集命令不变，不需要增加并发参数。

离线重试（在仓库目录中，使用已安装项目依赖的 Python）：

```powershell
python retry_description_ocr.py "output\runs\本轮目录\jobs.json"
python retry_description_ocr.py "output\runs\本轮目录\jobs.json" --job-id "指定岗位ID"
```

默认只处理有清单的失败/待识别岗位。指定岗位 ID 时会重新识别该岗位。
命令更新原 JSON，并导出同名 CSV；Excel 占用 CSV 时，JSON 更新仍然保留。
离线重试不会补采没有完整截图的岗位。

## 耗时与验证

- `description_page_seconds`：页面处理耗时，包括需要时的截图及人工登录等待。
- `description_capture_seconds`：分段截图及清单准备耗时。
- `description_ocr_seconds`：本地识别与合并耗时，不含工作器创建模型的时间。
- `description_ocr_worker_seconds`：工作器总耗时，首次调用包含模型初始化。
- `detail_pipeline_seconds`：全部详情处理的墙钟耗时，包含页面间隔和最后等待 OCR。

这些阶段有重叠，不能将各字段直接相加当作总耗时。实际收益取决于 OCR 岗位比例和机器资源。
测试覆盖先完整截图后识别、坐标恢复、后台重叠、单线程写结果、队列上限、登录重试、
中断/验证页后回收、失败隔离、导出等待和离线重试。正式站点的端到端速度仍需用同样样本测量。
